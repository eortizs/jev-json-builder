# Jev JSON Builder (JJB)

The "inward" approach to building structured JSONs is what actually unlocks systems with immediate response and native intelligence.

When AI is integrated directly into the backend for decision-making, the top priority stops being "conversation" and becomes infrastructure: imperceptible latency, predictable resource consumption, and direct compatibility with existing systems (APIs, databases, microservices).

The project is defined as **Jev JSON Builder (JJB)** — an Express middleware that turns natural-language input into a strictly-typed JSON payload using TypeSafe Jev (System One), without a generative LLM and without MCP middleware.

This document is the **concept** overview. For the middleware API, examples, and runnable demo, see [`README.md`](./README.md).

---

## The corrected concept (what the implementation actually does)

### The flaws JJB avoids

1. **High latency.** Generative LLM token streaming takes seconds — incompatible with immediate-response UX.
2. **Brittle syntactic parsing.** LLMs hallucinate fields, drop commas, append prose; you end up wrapping them in Zod/Pydantic + retries.
3. **Prohibitive output cost.** Paying for an LLM to emit static syntax (`{ "type": "..." }`) is wasteful.

### What JJB replaces

JJB replaces the **generative-LLM + tool-calling layer** whose only job was to produce structured arguments. It does **not** replace MCP as a tool-integration protocol — when MCP's role is limited to scaffolding structured tool calls for an LLM, that entire layer becomes unnecessary. Other MCP uses are out of scope.

### Architecture

```
[User Input]
    │
    ⚡ NIVEL 1 (optional): jevRouter — one `choice` (`route`) + one `noul` (`_hazard`) (~80-100ms)
    │      hazard fires → 422 before any extraction
    │      low route confidence → COMPLEX_LLM_AGENT (System Two, injected `onComplex`)
    │      FAST_JSON_PAYLOAD ↓
    ⚡ ONE request: state + all questions evaluated server-side in parallel (~100ms)
    ▼
┌─────────────────────────────────────────────────────────┐
│ Jev: enum Choices │ score Scores │ noul *_stated │ hazard│
└──────────────────────────┬──────────────────────────────┘
                           │ typed answers + probabilities + confidence
                           ▼
                  [Dual Gates] ── low ──▶ [Reject / Human Review / System Two]
                           │ high
                           ▼
           [Native JSON Assembly in your code]
           (closed-set keys, optional fields omitted, numbers normalized)
                           ▼
                [Express handler with req.jev typed]
```

The Level-1 router turns JJB into a **hybrid orchestration framework (System 1 + System 2)**: structured, parameter-explicit prompts never touch a generative LLM, and ambiguous/creative ones are handed to your heavy agent with the router's decision on `req.jevRoute`. See the README's "Hybrid orchestration router" section.

### The four core pillars

1. **No prose generation, negligible output cost.** Jev returns mathematical probabilities over precise options. No JSON syntax is ever generated by the model. The response `usage` reports only small decision tokens.
2. **Single-request speculative fan-out.** All questions for one request go in **one** `systemOne` call. Jev evaluates them concurrently server-side; your code filters irrelevant answers afterwards.
3. **Type-safe native compilation.** Your TypeScript code compiles the JSON. Jev only fills semantic variables using closed-set criteria whose **keys are the payload values themselves** — invalid keys are physically impossible.
4. **Dual gates — ambiguity vs. adversarialness.** `confidence` (distribution spread) gates **ambiguity**; a dedicated `noul` screens **prompt injection / hazards**. Thresholds scale with risk.

### Field-type playbook

| JSON field type | How JJB fills it | Mechanism |
| --- | --- | --- |
| Closed-set enum | `enumField(criteria, opts)` → `choice` | Criteria keys ARE the payload values |
| Optional field | `{ optional: true }` → `noul` `<name>_stated` | Field omitted when not stated |
| Ordered level / bucket | `scoreField(levels, opts)` → `score` | Score = position on your level spectrum (float 0..N-1) |
| Arbitrary number | `intField` / `numberField` → regex candidates + `choice` | Code normalizes the selected verbatim value |
| Free text | Not JJB's job | Pass through or route to a generative model |

### Validation status

- 51 unit tests pass (zero network; mock `TypeSafeClient` via fetch injection).
- `npm run demo` serves an interactive **playground** (`/playground`) plus four routes: `/api/animation`, `/api/triage`, `/api/orders`, `/api/orchestrate` (semantic router: FAST → JJB, COMPLEX → injected agent) — each response carries the typed payload and `meta` (model, raw answers with probabilities + confidence, token usage, `elapsedMs`).
- `demo/benchmark.ts` measures JJB end-to-end (p50/p95 wall, `systemOne` time, tokens) with optional generative-LLM baseline; mock mode isolates pipeline overhead, and without `LLM_API_KEY` it prints a labeled heuristic estimate instead of fabricated numbers.
- Live run requires `TYPESAFE_API_KEY`; without it, requests return 502 `jev_upstream_error`.
